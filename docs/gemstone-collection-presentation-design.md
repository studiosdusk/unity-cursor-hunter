# 젬스톤 흡수와 획득량 표시 연출 기획

2026-10-28 · 구현 전 기획안

몬스터가 처치된 자리에서 젬스톤이 짧게 튀어나오고, 각각 조금씩 다른 곡선을 따라 HUD로 가속해 빨려 들어간다. 해당 젬의 TargetPoint에 도착할 때만 화면의 획득량이 상승하고, Text (TMP)가 짧게 커졌다 돌아온다. 여러 처치가 겹치면 개별 젬들이 하나의 지속적인 수집 흐름으로 이어진다.

목표는 보상을 정확하게 읽을 수 있으면서도 사냥이 빨라질수록 수집의 밀도와 리듬이 풍성해지는 것이다. 아래 시간·개수·성능 수치는 첫 구현의 조정 기준이며, 출시 판정은 목표 기기의 실측과 실제 게임 화면으로 한다.

## 현재 프로젝트에서 확인한 조건

| 현재 구조 | 설계에 반영할 내용 |
|---|---|
| `CombatRunController.ApplyBundle`에서 처치 보상 집계 | 피해 이벤트가 아닌 최종 보상 확정 지점에서 연출 이벤트 발행 |
| 가넷과 확률형 추가 젬, 유물 배율·추가 드롭·소수 이월 존재 | UI가 원본 드롭 금액을 추측하거나 확률을 다시 굴리지 않음 |
| `MonsterCombatTarget.TryClaimKillSettlement`로 중복 정산 차단 | 부활한 동일 개체의 두 번째 죽음에는 수집 연출도 중복 생성하지 않음 |
| `DamageApplied`는 보상 집계보다 먼저 발생 | 이 이벤트만으로 획득량이나 드롭 연출을 만들지 않음 |
| 현재 `CombatGemstoneList`가 실제 누적량을 매 프레임 바로 표시 | 실제 누적량과 도착 기준 표시량을 분리해야 함 |
| 6종 행과 각 행의 `TargetPoint`가 Main에 존재 | 기존 행·아이콘·색상·상단 1개와 하단 2열 구성 재사용 |
| `TargetPoint`는 현재 행 중앙 | 구현 때 각 행의 젬 아이콘 중앙에 맞춰 흡수 착점으로 사용 |
| `TextSettingIgnore`와 검은 외곽선·그림자 폰트 | 숫자의 색과 가독성을 유지하고 크기만 짧게 반응 |
| Main Canvas는 Screen Space Overlay, 기준 해상도 1920×1080 | 월드 위치를 화면 좌표로 투영한 뒤 효과 Canvas 좌표로 변환 |
| 종료 시 `PresentationReset`이 결과 전달 전에 발생 | 젬 연출은 이 신호로 바로 지우지 않고 App의 결과 전달로 마무리 |
| 현재 파일에서 `PlayerProgressionPresentation(Clone)` 및 DOTween 패키지를 확인하지 못함 | 구현 첫 단계에서 실제 생성 주체·패키지 버전·asmdef 참조 확인. 이름 문자열 검색을 런타임 연결 수단으로 삼지 않음 |

관련 구현은 [CombatRunController](../Assets/CursorHunter/Combat/Runtime/CombatRunController.cs), [MonsterCombatTarget](../Assets/CursorHunter/Combat/Runtime/MonsterCombatTarget.cs), [CombatGemstoneList](../Assets/CursorHunter/App/Runtime/CombatGemstoneList.cs), [RunCoordinator](../Assets/CursorHunter/App/Runtime/RunCoordinator.cs), [HuntManager](../Assets/CursorHunter/App/Runtime/HuntManager.cs)를 기준으로 한다.

## 플레이어에게 보이는 한 번의 수집

| 단계 | 시작 기준 시간 | 동작과 목적 |
|---|---|---|
| 등장 | 처치 후 0~50ms 안 | 몬스터 몸 중심에서 젬이 작은 크기로 나타나 즉시 읽히는 크기로 확대 |
| 분출 | 약 100~150ms | 젬이 18~48 기준 px 정도 짧게 튄다. 실제 Rigidbody 충돌 대신 통제된 곡선 사용 |
| 전환 | 약 30~70ms | 흩어지는 속도가 잠깐 느려지며 종류와 출처가 읽힘. 바닥에서 오래 기다리지 않음 |
| 흡수 | 약 280~520ms | 목표 방향으로 부드러운 곡선을 그리며 가속. 같은 처치의 젬은 12~28ms씩 시차 |
| 착점 | 마지막 50~80ms | 젬이 작아지며 TargetPoint 안으로 들어감. 수집량 도착 처리와 작은 흡수광 발생 |
| 숫자 반응 | 도착과 같은 프레임 | 숫자 팝업 시작. 획득량은 80~160ms 동안 짧게 상승 후 정확한 정수에 정착 |

일반적인 처치부터 도착까지 약 0.45~0.80초를 목표로 한다. 먼 모서리에서도 대기까지 포함해 0.95초를 넘기지 않는다. 짧은 거리에는 최소 비행 시간을 두어 젬이 순간 이동처럼 사라지지 않게 한다.

초기 조정값은 기본 젬 크기 20~30 기준 px, 추가 젬 24~34px, 회전 ±20도, 경로 굴곡 24~80px다. 모두 1920×1080 기준 Canvas 단위이며 실제 화면 배율을 반영한다. 곡선의 끝은 반드시 TargetPoint이며 원을 돌거나 목표 근처에서 망설이는 동작은 넣지 않는다.

분출 방향과 궤적의 흔들림에는 별도 연출 난수를 사용한다. 전투의 드롭·치명타 난수 상태는 연출 때문에 변하지 않는다.

## 풍성함과 전투 가독성

수집이 적을 때는 젬 하나의 출발·곡선·도착이 분명해야 한다. 광역 처치에서는 여러 위치에서 출발한 젬들이 약간의 시차를 두고 HUD로 모여들어야 한다. 화면 전체를 하얀 빛으로 덮거나 모든 오브젝트가 같은 직선·동일 타이밍으로 움직이는 연출은 피한다.

- 비행 중에는 짧은 잔상 1~2개를 제한적으로 사용한다. 밝은 트레일은 추가 젬 또는 큰 보상에 우선 배정한다.
- 데미지 숫자, 커서, 공격 경고와 경쟁하지 않도록 비행 젬은 작은 크기를 유지한다. 전투 입력을 받지 않는 별도 효과 계층에 둔다.
- HUD에 가까워지면 효과는 숫자보다 뒤로 지나간다. 숫자 앞에서 입자가 터지지 않으며 아이콘 주위에서만 짧게 사라진다.
- 가넷은 빠르고 가벼운 기본 수집음, 추가 젬은 조금 더 맑은 음색과 10~15% 큰 비주얼로 구별한다. 현재 데이터에는 별도 희귀도 필드가 없으므로 젬 이름만으로 임의의 희귀도 등급을 추가하지 않는다.
- 전역 화면 흔들림, 큰 화이트 플래시, 매 처치의 긴 광선은 사용하지 않는다.
- 하단 2열은 그대로 유지한다. 비행 중인 종류의 행을 불필요하게 비활성화하거나 재정렬하지 않는다.

## 표시용 젬과 실제 금액

실제 보상 1개가 반드시 비행 오브젝트 1개를 뜻하지는 않는다. 한 오브젝트는 양의 정수 금액을 담은 표시용 묶음이다. 예를 들어 가넷 120개는 40개씩 담은 3개 젬으로 보일 수 있고, 토파즈 1개는 1개 젬으로 보인다. 분할 금액의 합은 항상 원래 금액과 정확히 같아야 한다.

| 상황 | 초기 표시 정책 |
|---|---|
| 일반 처치의 가넷 | 종류별 보상 묶음당 1~3개, 큰 묶음도 최대 4개 |
| 추가 젬 드롭 | 1~2개, 금액이 1이면 1개 |
| 빠른 연속 처치 | 우선 각 출처의 대표 젬을 남기고 추가 장식 개수를 줄임 |
| 한 프레임 다수 처치 | 같은 종류·가까운 위치·80ms 이내 사건을 묶어 시차를 둔 흐름으로 표시 |
| 효과 포화 | 보상은 모두 기록하고 표시 묶음만 합침. 출발 대기열을 무한히 쌓지 않음 |

정상 상태에서는 모든 보상 있는 처치 위치에 대표 출발점이 보인다. 포화 시에는 가까운 출처끼리만 합치며, 맵 양 끝의 처치를 한 위치에서 나온 것으로 표시하지 않는다. 화면 밖 출처는 화면 가장자리의 안전한 지점으로 제한한다.

기본 풀은 전투 진입 전에 128개를 준비한다. 동시 활성 상한도 128개로 고정한다. 가넷이 최대 96개까지만 사용하게 해 추가 젬에 최소 32개의 여유를 둔다. 전체 신규 비행은 초당 약 160개를 시작점으로 조절하고, 긴 프레임 뒤 밀린 생성량을 한 번에 발사하지 않는다. 이 값은 성능 보장이 아닌 프로파일링 출발점이다.

포화 처리는 장식 축소 → 공간별 보상 합치기 → 대기 없는 간소화 도착 순서다. 대표 비행조차 배정할 수 없는 상황에서는 해당 금액을 가장 가까운 같은 종류의 도착 묶음에 포함한다. 그런 묶음도 없으면 정해진 짧은 지연 후 작은 HUD 반응으로 반영한다. 숨겨진 보상과 영구적인 표시 지연은 허용하지 않는다.

## 숫자 팝업과 증가 리듬

첫 가넷 숫자는 기준 스케일의 최대 1.12배, 하단 숫자는 최대 1.16배로 설정한다. 약 50~65ms 동안 커지고 130~170ms 동안 원래 크기로 돌아온다. 크게 획득해도 1.18배를 넘지 않는다. 인접 숫자·아이콘을 침범하는지 실제 최대 자릿수로 검수한다.

GridLayoutGroup이 관리하는 행 루트는 확대하지 않는다. Text (TMP) 또는 그 전용 시각 부모만 DOTween으로 움직이고, TargetPoint와 배경은 고정한다. 흡수 착점이 숫자 팝업에 끌려 움직이면 안 된다.

동일 종류의 도착은 약 60ms 창으로 묶어 수량을 갱신한다. 팝업은 종류별 최소 150ms 간격으로 강도를 갱신한다. 숫자 도착량은 매번 반영하되 화면은 지속적으로 읽을 수 있는 짧은 탄성을 유지한다.

연속 도착 중에는 현재 스케일에서 다음 반응으로 이어진다. 매번 1로 강제 리셋하거나 Punch Tween을 겹쳐 쌓지 않는다. 마지막 도착 후 0.25초 이내에는 원래 크기로 돌아온다. 작은 아이콘 흡수광도 종류별 하나만 유지한다.

숫자 증가와 팝업은 독립적이다. 숫자 트윈을 재시작할 때마다 완료 시점을 뒤로 밀면 지속 수집 중 잔액이 계속 늦어지므로, 현재 짧은 갱신 창의 종료 시점은 유지하고 목표만 올린다. 감소·역행·최종값 초과는 허용하지 않는다.

금액은 전 과정에서 Int64를 유지한다. 큰 금액을 float로 변환해 최종 숫자를 계산하지 않는다. 보간이 필요하면 정확한 시작·목표 정수를 보관하고 제한된 0~1 진행률로 차이만 계산하며 종료 시 목표 정수를 직접 대입한다. 출시 전 `long.MaxValue` 근처와 표시 단위 전환도 검수한다. 이번 연출에서 K/M 축약 규칙을 새로 도입하지는 않는다.

## 실제 획득량과 화면 표시량

실제 보상은 기존 전투 규칙이 정하는 시점에 기록한다. 젬의 비행 성공 여부나 DOTween 완료 콜백이 영구 지갑을 수정해서는 안 된다. 영구 지급은 기존 `RunResult → App → Progression`의 정산 정책을 유지한다.

종류별로 다음 값을 따로 관리한다.

| 값 | 의미 |
|---|---|
| 실제 획득량 A | Combat이 이미 확정한 이번 전투 보상 |
| 도착 누적량 C | 비행 또는 간소화 도착 처리가 완료된 표시 금액 |
| 화면 표시량 D | 현재 Text (TMP)에 표시하는 보간 중 정수 |
| 미도착량 | 아직 비행 중이거나 표시 대기인 금액 A−C |

항상 `0 ≤ D ≤ C ≤ A`를 유지한다. 모든 연출이 끝나면 `D = C = A`다. 예를 들어 실제 가넷이 100에서 112로 늘어도 도착 전 HUD는 100을 유지한다. 금액 4씩 담은 세 젬이 도착하면 목표는 104 → 108 → 112가 된다.

현재 `CombatGemstoneList.ShowRunning`의 직접 숫자 덮어쓰기는 제거하고, 행의 표시 여부만 현재 전투 데이터와 맞춘다. 수량은 표시 전담 컨트롤러가 유일하게 쓴다. UI가 새로 만들어지거나 효과 기능이 꺼진 경우에는 실제 누적량과 즉시 동기화하는 명시적 경로를 둔다.

## 보상 사건과 중복 방지

추가할 `CombatRewardResolved`는 제안 이름이며 아직 존재하지 않는 타입이다. 한 처치에서 최종 확정된 보상들을 묶어서 알린다.

- `RunId`, 런 내 증가하는 보상 사건 번호, 재화별 최종 증가량, 적용 전 캡처한 출발 월드 위치를 포함한다.
- 출발점은 사망 연출이 몬스터를 비활성화하기 전에 얻은 몸 중심이다. 현재 `DamageTextPosition`은 체력바/머리 위 위치이므로 그대로 재사용하지 않는다.
- 중복 처치 차단과 확률·유물·소수 이월·오버플로 검사를 거쳐 실제 장부에 기록한 증가량만 전달한다. 같은 ID가 기본/추가 보상으로 겹치면 정규화한다.
- 보상 계산·검증과 기록의 경계를 정리해 숫자 오버플로 실패 후 일부 보상만 표시되는 경우를 막는다. 드롭 확률과 실제 지급 정책은 바꾸지 않는다.
- `(RunId, 사건 번호)`로 중복 소비를 막는다. 풀 오브젝트는 별도의 재사용 세대 번호를 검사해 이전 비행의 콜백이 새 비행을 완료시키지 못하게 한다.
- 사건이 없거나 금액이 0인 사망에는 획득 젬을 만들지 않는다. 부활·반복 타격·대상 파괴가 추가 획득의 근거가 될 수 없다.

전투 난수와 표시 난수는 분리한다. 소비자는 몬스터 GameObject의 생존에 의존하지 않고 사건에 복사된 값만 사용한다.

## TargetPoint 연결과 화면 좌표

사용자가 지칭한 `PlayerProgressionPresentation(Clone)`가 실제 런타임 HUD 루트라면 생성 직후 그 인스턴스의 재화 ID별 바인딩을 등록한다. 현재 체크아웃의 Main에는 `GemStoneLists`와 6개 행이 있으므로 이 구성을 우선 연결 대상으로 삼는다. 두 경우 모두 `gem.garnet` 같은 고정 ID로 TargetPoint·텍스트·아이콘을 연결한다.

`GameObject.Find("PlayerProgressionPresentation(Clone)")`나 반복적인 이름 검색은 사용하지 않는다. 직렬화 참조 또는 HUD 생성자가 넘긴 참조를 사용하며, 해당 HUD를 해제할 때 등록도 함께 해제한다.

월드 카메라의 처치 위치를 화면에 투영하고 효과 Canvas의 로컬 좌표로 변환한다. Overlay Canvas는 UI 카메라가 없다는 현재 구성을 반영한다. 비행은 전용 효과 Canvas 안에서 수행하고 매 프레임 몬스터를 따라다니지 않는다.

화면 비율·해상도·UI 배율이 바뀌거나 행이 활성화되면 레이아웃 확정 후 여섯 착점만 다시 계산한다. 비행 중 목표 위치는 최신 착점으로 부드럽게 이어간다. 창 크기 변경 때문에 원래 목적지에 도착한 뒤 순간 이동하는 현상을 허용하지 않는다.

비행 계층은 게임 필드 위, HUD 숫자 아래에 둔다. GraphicRaycaster와 Raycast Target을 사용하지 않는다. 빈 HUD 영역 전체를 덮는 투명 패널로 전투 입력을 막지 않는다.

## DOTween과 풀의 소유권

젬마다 풀에서 재사용하는 진행률 Tweener 하나로 등장·분출·가속·축소를 평가한다. 숫자 행에는 각각 최대 하나의 스케일 Tweener와 수량 Tweener를 둔다. 매 처치마다 여러 Sequence와 캡처 람다를 만드는 방식은 기본 구현에서 제외한다.

Tweener는 초기화 때 만들고 재사용한다. 고정된 풀 슬롯이 보유하는 트윈은 `SetAutoKill(false)`로 유지하고 명시적으로 정지·되감기·해제한다. 풀 반환 시 위치·스케일·알파·색·표시 금액·사건 번호를 모두 초기화한다. DOTween 용량은 프로젝트의 다른 사용자까지 고려해 미리 설정한다. 재사용·수명주기 API는 [DOTween 공식 문서](https://dotween.demigiant.com/documentation.php)를 따른다.

일시정지는 이 연출 소유자의 시계로 제어한다. 현재 전투 일시정지가 항상 `Time.timeScale = 0`을 뜻하지 않으므로, 전역 시간 배율만 믿지 않는다. 전용 Tweener를 Manual 업데이트하거나 소유 그룹만 명시적으로 Pause/Play한다. 전체 게임의 `DOTween.KillAll`·`Clear`를 호출하지 않는다.

`SetLink`를 보조적으로 쓰더라도 풀 반환·씬 해제·구독 해제는 직접 처리한다. Sequence 내부의 자식 Tweener에 건 `SetLink`만으로 수명주기를 보장하지 않는다. [DOTween 공식 수명주기 설명](https://dotween.demigiant.com/documentation.php#settings)

## 종료와 예외 상황

| 상황 | 사용자에게 보이는 동작과 정확성 |
|---|---|
| 시간 만료·정상 완료 | 전투와 정산은 먼저 확정. 남은 젬을 최대 0.30초 동안 빠르게 흡수한 뒤 결과 화면 표시 |
| 마지막 순간의 추가 드롭 | RunResult와 표시 장부를 대조해 누락분까지 마지막 수집에 포함 |
| 사용자가 즉시 결과/다음 화면으로 이동 | 기다리게 하지 않고 최종 표시량을 확정한 뒤 잔여 연출 회수 |
| 메인 메뉴 복귀·Reset | 비행·팝업·대기량을 즉시 정리하고 0으로 초기화. 실제 지급은 기존 SettlementPolicy 유지 |
| 새 전투 시작 | 새 RunId와 표시 세대로 시작. 이전 완료 콜백은 무시 |
| 검사창·수동 일시정지·포커스 상실 | 비행·숫자·소리를 함께 정지. 복귀 시 남은 시간부터 재개 |
| HUD 비활성화·교체 | 예전 바인딩 해제. 같은 런의 새 HUD에는 누적 사실을 재동기화 |
| 착점·아이콘·폰트 누락 | 실제 금액은 보존하고 해당 행에 즉시 동기화. 반복 로그를 제한하고 개발 빌드 진단에 표시 |
| 숫자 오버플로·시작 실패 | 기존 실패 정책을 우선하며 성공하지 않은 지급을 흡수 연출로 보여주지 않음 |

현재 `PresentationReset`을 젬의 즉시 회수 신호로 사용하면 정상 종료의 마지막 흡수도 사라진다. 데미지 숫자의 기존 초기화는 유지하고, 젬은 App에서 별도의 `FinishPresentation(result)`와 `CancelPresentation()` 경로로 관리한다. 이름은 제안이며 구현 시 정한다.

종료의 0.30초는 시각적 마무리 상한이다. 저장·지급 성공 여부를 애니메이션 완료에 매달거나 화면 이동을 막는 대기열로 만들지 않는다.

## 소리와 접근성

도착 순간의 짧고 둥근 수집음을 중심으로 한다. 모든 젬에 소리를 하나씩 재생하지 않고 50~80ms 이내의 도착을 묶는다. 전체 발음은 초당 약 10회, 동시 음성은 최대 8개에서 시작해 조정한다. 연속 흡수의 피치는 약 0.96~1.12 범위에서 완만하게 변하고 0.35초 이상 끊기면 돌아온다. 계속 높은 음으로 치솟는 연출은 넣지 않는다.

추가 젬 소리가 가넷에 묻히지 않도록 우선순위를 주고, 전투의 경고음을 가리지 않도록 믹서에서 상대 음량을 조정한다. 숫자 상승은 소리 없이도 이해할 수 있어야 한다.

효과 감소 설정에서는 표시 개수를 줄이고 분출·회전·잔상을 생략한다. 약 0.18~0.25초의 짧은 비행과 최대 1.05배 팝업을 사용한다. 이 설정에서 보상량·표시 순서·드롭 확률은 변하지 않는다.

## 구현 책임과 순서

| 순서 | 작업 | 확인하고 넘어갈 조건 |
|---|---|---|
| 1 | 실제 HUD 생성 위치, DOTween 설치/라이선스/asmdef, 6종 ID 바인딩 확인 | 이름 검색 없이 6개 TargetPoint와 TMP를 찾을 수 있음 |
| 2 | Combat의 최종 보상 사건과 App의 표시 장부 | 확률·유물·부활·중복·오버플로에서 금액이 정확함 |
| 3 | 고정 스냅샷 Sandbox에서 젬 1종의 풀·비행·도착·팝업 | 출발점과 도착 프레임이 맞고 재시작에 안전함 |
| 4 | Main 6종, 2열 HUD, 카메라/Canvas 변환과 종료 처리 | 실제 전투 시작·진행·정산·메뉴 복귀 연결 통과 |
| 5 | 대량 합치기, 잔상, 오디오, 효과 감소, 성능 조정 | 목표 기기의 스트레스 테스트와 아트 검수 통과 |

Combat은 보상 사실을 만들고 App의 표시 계층이 HUD·풀·DOTween을 소유한다. Combat이 Progression의 지갑이나 Data의 아이콘 카탈로그를 직접 읽지 않는다. App은 기존 `GemstoneIconCatalog`를 사용한다. 공급사 원본은 수정하지 않고 게임 소유의 효과 프리팹과 조정 에셋을 둔다.

제안 구성은 `CombatRewardResolved` 사건, `GemstoneCollectionPresenter` 총괄, `GemstoneFlyView` 풀 항목, `GemstoneCounterPresenter` 행별 표시, `GemstoneCollectionSettings` 조정값이다. 마지막 네 이름은 구현 예정 역할을 설명하며 기존 타입으로 가정하지 않는다. 공용 전역 이벤트 버스는 추가하지 않는다.

## 출시 판정 기준

| 검수 | 합격 조건 |
|---|---|
| 1마리 처치 | 출처가 몸 위치와 맞고, 도착 전 숫자가 오르지 않으며 도착에 맞춰 반응 |
| 80마리 동시 처치 | 표시 상한을 지키며 모든 실제 보상 합계가 정확하고 추가 젬도 눈에 띔 |
| 합성 이벤트 200회/초 10초 | 대기열·풀·트윈·음성이 상한 안에서 유지되고 종료 후 모두 회수 |
| 마지막 프레임 처치 | 추가 드롭까지 결과와 HUD가 정확히 일치하며 마무리가 0.30초를 넘지 않음 |
| 연속 재시작 100회 | 이전 RunId의 효과·콜백·숫자가 새 런으로 넘어오지 않음 |
| 부활 재처치 | 동일 개체가 보상과 수집 젬을 중복 생성하지 않음 |
| 해상도·비율·배율 변경 | 16:9, 16:10, 21:9 및 지원 최소 창 크기에서 착점과 HUD가 어긋나지 않음 |
| 큰 수량 | Int64 정밀도, 단조 증가, 최종값 정확성, 숫자 잘림과 팝업 겹침 검사 통과 |
| 효과 감소·음소거 | 금액과 완료 시점의 정확성은 동일하며 필수 정보가 사라지지 않음 |
| CPU·메모리 | 워밍업 후 비행·큐·풀 관리의 GC 할당 0B/frame 목표. TMP 문자열 비용은 분리 측정 |
| 프레임 시간 | 목표 최소 기기 60fps 기준 이 기능의 CPU 증가분 p95 0.5ms 이하, p99 1ms 이하를 초기 예산으로 측정 |
| UI 비용 | 비행 때문에 특성 화면·전체 HUD의 큰 Canvas가 매 프레임 재빌드되지 않음 |

플랫폼과 최소 사양이 확정되지 않았으므로 성능 합격 수치는 해당 기기에서 최종 조정한다. 에디터 평균 FPS나 브라우저 미리보기로 출시 성능을 주장하지 않는다. Frame Debugger·Profiler로 Canvas 재빌드, 배치, 오버드로, 스파이크, 활성 트윈 수를 함께 확인한다. 동적인 UI를 별도 Canvas로 분리하고 비상호작용 UI의 Raycast를 끄는 근거는 [Unity의 UI 최적화 지침](https://unity.com/how-to/unity-ui-optimization-tips)을 따른다.

기획 미리보기는 분출·흡수·도착·팝업의 리듬을 논의하기 위한 것이다. Unity 런타임, DOTween 연결, 실제 사운드와 성능은 구현 및 검수 단계에서 완성한다.
