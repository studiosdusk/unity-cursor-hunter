# 젬스톤 흡수와 획득량 표시 연출 기획

2026-10-28 · 구현 및 조정 기준 · 소/중/대 1·5·10, Main Inspector 및 수량 텍스트 착점

몬스터가 처치된 자리에서 젬스톤이 짧게 튀어나오고, 각각 조금씩 다른 곡선을 따라 해당 종류의 **획득 수량 Text (TMP) 중심**으로 가속해 빨려 들어간다. TargetPoint는 이 텍스트 중심의 흡수 착점이다. 여기에 도착할 때만 화면의 획득량이 상승하고, Text (TMP)가 짧게 커졌다 돌아온다. 여러 처치가 겹치면 개별 젬들이 하나의 지속적인 수집 흐름으로 이어진다.

목표는 보상을 정확하게 읽을 수 있으면서도 사냥이 빨라질수록 수집의 밀도와 리듬이 풍성해지는 것이다. 아래 시간·개수·성능 수치는 첫 구현의 조정 기준이며, 출시 판정은 목표 기기의 실측과 실제 게임 화면으로 한다.

## 구현과 사용 방법

- Main 씬 루트의 `GemstoneCollectionController`를 선택한다. 설정은 `Settings`의 `Sizes / Motion / Counter / Sound / Budget`에서 조절한다. 소·중·대 액면가는 1·5·10으로 고정이다.
- 6종 수량 TMP와 고정 TargetPoint, 전용 비행 Canvas, 풀 프리팹, 두 종류의 짧은 수집음을 씬에 연결했다. 배경 위·숫자 아래로 비행하고 텍스트 중심에서 도착 처리한다.
- 실제 플레이를 켠 뒤 전투가 진행 중이지 않을 때 Inspector의 `43개`, `48개`, `80마리 × 43개`로 시험한다. 테스트는 전투 표시 화면만 잠시 보여주며 지급·저장을 호출하지 않는다. 종료하면 원래 화면과 수량으로 복원한다.
- Play Mode에서 바꾼 연출값은 새 발사부터 적용한다. `현재 조정값 복사` → Play Mode 종료 → `조정값 붙여넣기` → Main 씬 저장으로 조정값을 보존한다. 연결 참조는 Edit Mode에서 편집하며 풀·음성 개수는 다음 런 준비 시 다시 구성한다.
- `CombatRunController.RewardResolved`는 최종 정수 보상을 원자적으로 기록한 후 `CombatRewardResolved` 값을 전달한다. `CombatGemstoneList`는 활성 종류를 관리하고, 연결된 컨트롤러가 도착 수량과 TMP를 쓴다. 컨트롤러가 꺼지면 목록은 실제 수량을 직접 표시한다.
- `GemstoneFlyView` 풀과 `GemstoneCounterPresenter`는 소유한 DOTween만 재사용·해제한다. 전투 일시정지·포커스 상실 때 비행·숫자·소리를 함께 멈추며, 종료 시 최대 0.30초 후 결과를 표시한다.
- 에디터/고정 스냅샷 검증과 Main PlayMode 검증은 수행한다. 아래 성능 예산은 실제 출시 최소 사양에서 별도로 측정할 목표이며 자동 테스트 통과를 GPU·프레임 성능 보장으로 해석하지 않는다.

아래의 구조 분석 표는 구현 착수 당시의 상태와 변경 이유를 기록한다.

## 플레이어에게 보이는 한 번의 수집

| 단계 | 시작 기준 시간 | 동작과 목적 |
|---|---|---|
| 등장 | 처치 후 0~50ms 안 | 몬스터 몸 중심에서 젬이 작은 크기로 나타나 즉시 읽히는 크기로 확대 |
| 분출 | 약 100~150ms | 젬이 18~48 기준 px 정도 짧게 튄다. 실제 Rigidbody 충돌 대신 통제된 곡선 사용 |
| 전환 | 약 30~70ms | 흩어지는 속도가 잠깐 느려지며 종류와 출처가 읽힘. 바닥에서 오래 기다리지 않음 |
| 흡수 | 약 280~520ms | 목표 방향으로 부드러운 곡선을 그리며 가속. 같은 처치의 젬은 12~28ms씩 시차 |
| 착점 | 마지막 50~80ms | 젬이 작아지며 TargetPoint 안으로 들어감. 수집량 도착 처리와 작은 흡수광 발생 |
| 숫자 반응 | 도착과 같은 프레임 | 숫자 팝업 시작. 획득량은 80~160ms 동안 짧게 상승 후 정확한 정수에 정착 |

일반적인 처치부터 도착까지 약 0.45~0.80초를 목표로 한다. 개별 젬의 발사 후 도착은 먼 모서리에서도 0.95초 이내로 맞춘다. 대량 처치로 풀 대기가 생기면 여러 차례 나눠 발사하므로 처치부터 최종 도착까지는 더 길어질 수 있다. 짧은 거리에는 최소 비행 시간을 두어 젬이 순간 이동처럼 사라지지 않게 한다.

초기 크기는 소 22px·중 30px·대 40px, 회전 ±20도, 경로 굴곡 24~80px다. 모두 1920×1080 기준 Canvas 단위이며 실제 화면 배율을 반영한다. 크기 차이는 젬의 종류나 희귀도가 아니라 1·5·10의 수량 차이를 의미한다. 곡선의 끝은 반드시 TargetPoint이며 원을 돌거나 목표 근처에서 망설이는 동작은 넣지 않는다.

분출 방향과 궤적의 흔들림에는 별도 연출 난수를 사용한다. 전투의 드롭·치명타 난수 상태는 연출 때문에 변하지 않는다.

## 풍성함과 전투 가독성

수집이 적을 때는 젬 하나의 출발·곡선·도착이 분명해야 한다. 광역 처치에서는 여러 위치에서 출발한 젬들이 약간의 시차를 두고 HUD로 모여들어야 한다. 화면 전체를 하얀 빛으로 덮거나 모든 오브젝트가 같은 직선·동일 타이밍으로 움직이는 연출은 피한다.

- 비행 중에는 짧은 잔상 1~2개를 제한적으로 사용한다. 밝은 트레일은 추가 젬 또는 큰 보상에 우선 배정한다.
- 데미지 숫자, 커서, 공격 경고와 경쟁하지 않도록 비행 젬은 작은 크기를 유지한다. 전투 입력을 받지 않는 별도 효과 계층에 둔다.
- HUD에 가까워지면 젬은 행 배경 위·숫자 글리프 아래로 지나가 수량 텍스트 중심에서 작아지며 사라진다. 작은 흡수광도 텍스트 뒤에서만 반응한다. 행 배경 뒤에 먼저 가려져 텍스트에 도착하기 전에 사라진 것처럼 보이지 않도록 효과 계층을 나눈다.
- 가넷은 빠르고 가벼운 기본 수집음, 추가 젬은 조금 더 맑은 음색과 짧은 흡수광으로 구별한다. 젬 종류에 따라 소·중·대 크기 규칙을 바꾸지 않는다. 현재 데이터에는 별도 희귀도 필드가 없으므로 젬 이름만으로 임의의 희귀도 등급을 추가하지 않는다.
- 전역 화면 흔들림, 큰 화이트 플래시, 매 처치의 긴 광선은 사용하지 않는다.
- 하단 2열은 그대로 유지한다. 비행 중인 종류의 행을 불필요하게 비활성화하거나 재정렬하지 않는다.

## 소·중·대와 정확한 수량 분해

모든 젬 종류에 같은 고정 규칙을 적용한다. 소형 한 오브젝트는 1개, 중형은 5개, 대형은 10개다. 한 처치에서 최종 확정된 **재화 종류별 금액**을 대 → 중 → 소 순으로 나눈다. 이 값은 Inspector에서 바꾸는 밸런스 값이 아니며 읽기 전용으로 표시한다.

```text
대형 개수 = amount / 10
중형 개수 = (amount % 10) / 5
소형 개수 = amount % 5
```

나눗셈은 양의 Int64 정수 나눗셈이다. 0이면 만들지 않고 음수 보상은 이 경로의 입력으로 받지 않는다. 분해는 금액에 비례하는 반복 없이 상수 시간에 계산한다.

| 보상 | 대형(10) | 중형(5) | 소형(1) | 비행 오브젝트 총수 |
|---|---:|---:|---:|---:|
| 1 | 0 | 0 | 1 | 1 |
| 5 | 0 | 1 | 0 | 1 |
| 9 | 0 | 1 | 4 | 5 |
| 10 | 1 | 0 | 0 | 1 |
| 43 | 4 | 0 | 3 | 7 |
| 48 | 4 | 1 | 3 | 8 |
| 120 | 12 | 0 | 0 | 12 |

가넷 43과 토파즈 6이 함께 나오면 가넷은 대 4·소 3, 토파즈는 중 1·소 1로 각각 자기 TargetPoint로 간다. 서로 다른 처치의 소형 5개를 중형 1개로 다시 교환하지 않는다. 보상 수량은 최종 확률·배율·소수 이월 계산 이후의 정수다.

각 젬은 자기 크기에 맞는 정확한 1·5·10만 도착 처리한다. 대형 4개와 소형 3개가 순서대로 도착하면 숫자의 목표값은 10 → 20 → 30 → 40 → 41 → 42 → 43이다. 실제 곡선 길이에 따라 도착 순서는 달라도 최종 합계는 같다. 젬 위에 작은 수량 문자를 덧씌우지는 않는다.

## 대량 처치와 풀 예산

한 번의 43개 보상은 반드시 7개 젬으로 보인다. 성능 때문에 대형 한 개에 40개를 담거나 7개를 3개로 줄이지 않는다. 이전 초안의 임의 금액 묶기·가상 도착 정책은 이 규칙으로 대체한다.

초기 풀 256개와 동시 활성 상한 256개를 전투 진입 전에 준비한다. 그중 64개는 추가 젬의 발사가 가넷에 막히지 않도록 예약한다. 일반 처치에는 12~28ms 시차를 사용하고, 광역 처치에는 여러 출처의 발사를 교차시킨다. 새 젬은 프레임당 최대 24개에서 시작해 조정한다. 상한은 목표 기기의 실측으로 정할 조정값이지 성능 보장이 아니다.

풀이 가득 차면 남은 **정확한 크기별 개수와 원래 출발 위치**를 보관하고 빈 슬롯이 생기는 대로 나눠 발사한다. 모든 작은 젬의 대기 GameObject나 Tween을 미리 만들지 않는다. 처치 사건 하나에 `남은 대/중/소 개수`만 보관하고 발사할 때 한 개씩 차감한다. 새 사건과 오래된 사건을 공정하게 순회해 특정 출처·추가 젬이 계속 밀리지 않게 한다.

압축 대기 항목은 우선 1,024개를 사전 확보한다. 필요한 전체 용량은 지원하는 최악의 한 런 생성량을 기준으로 결정하며, 준비 시 부족하면 런 시작 전에 확장한다. 런 중 예상을 넘으면 보상이나 크기별 개수를 버리지 않고 데이터 공간만 확장하며 개발 진단에 기록한다. 런 중 확장 발생은 성능 검수 실패로 취급한다. 장기 유입량이 처리량을 넘으면 대기가 늘 수 있으므로 활성 상한만으로 모든 부하가 해결됐다고 간주하지 않는다.

포화 시 먼저 잔상·흡수광을 줄이고, 대기 압력에 따라 분출·대기·비행 시간을 설정된 최소값까지 단축한다. 그래도 넘치면 개수 보존을 우선하고 여러 차례 수집한다. 기본 스트레스 사례는 80마리 × 가넷 43개 = 대형 320개·소형 240개, 총 560개를 모두 날리는 것이다. 일반 플레이에서는 2초 이내에 이 묶음을 비우는 것을 초기 목표로 삼는다.

현재 게임이 허용하는 보상 상한에서 개별 젬 수가 지나치게 커지면 액면가 10을 유지하면서 짧은 시간에 전부 보여주는 데 물리적 한계가 생긴다. Int64 최대값 테스트는 분해·보상 장부의 정확성 검사이며 그만큼의 오브젝트를 실제 생성하는 부하 검사가 아니다. 출시 범위의 최대 보상과 처치율로 따로 검수하고, 미달하면 풀·렌더링·타이밍을 조정한다. 액면가나 실제 지급량을 자동으로 바꾸지 않는다.

화면 밖 출처는 카메라 투영 후 화면 가장자리의 안전한 지점으로 제한한다. 서로 다른 몬스터 위치를 하나의 출처로 합치지 않는다. 정상 완료 시의 잔여 연출 정리는 아래 종료 규칙을 따르며, 이는 전투 중 개수 축소 정책이 아니다.

## 숫자 팝업과 증가 리듬

첫 가넷 숫자는 기준 스케일의 최대 1.12배, 하단 숫자는 최대 1.16배로 설정한다. 약 50~65ms 동안 커지고 130~170ms 동안 원래 크기로 돌아온다. 크게 획득해도 1.18배를 넘지 않는다. 인접 숫자·아이콘을 침범하는지 실제 최대 자릿수로 검수한다.

GridLayoutGroup이 관리하는 행 루트는 확대하지 않는다. 고정된 수량 표시 영역 중심에 TargetPoint를 두고, 같은 중심을 기준으로 Text (TMP) 또는 그 전용 시각 부모만 DOTween으로 확대한다. TargetPoint는 확대되는 Transform의 자식이 아닌 고정 부모 아래의 별도 자식으로 두고 팝업의 스케일을 상속하지 않는다. TMP는 수량 영역 가운데 정렬·중앙 피벗을 사용해 자릿수가 늘어도 숫자가 착점 주위에 유지되게 한다. 배경과 착점은 팝업 때문에 움직이지 않는다.

도착 누적량은 각 오브젝트 도착 프레임에 즉시 +1·+5·+10으로 반영한다. 같은 프레임의 도착은 합산해 TMP를 한 번만 갱신하고, 약 60ms 창은 팝업·흡수광·소리의 묶음 판단에만 사용한다. 팝업은 종류별 최소 150ms 간격으로 강도를 갱신한다. 숫자 도착량은 매번 반영하되 화면은 지속적으로 읽을 수 있는 짧은 탄성을 유지한다.

연속 도착 중에는 현재 스케일에서 다음 반응으로 이어진다. 매번 1로 강제 리셋하거나 Punch Tween을 겹쳐 쌓지 않는다. 마지막 도착 후 0.25초 이내에는 원래 크기로 돌아온다. 텍스트 뒤의 작은 흡수광도 종류별 하나만 유지한다.

숫자 증가와 팝업은 독립적이다. 숫자 트윈을 재시작할 때마다 완료 시점을 뒤로 밀면 지속 수집 중 잔액이 계속 늦어지므로, 현재 짧은 갱신 창의 종료 시점은 유지하고 목표만 올린다. 감소·역행·최종값 초과는 허용하지 않는다.

금액은 전 과정에서 Int64를 유지한다. 큰 금액을 float로 변환해 최종 숫자를 계산하지 않는다. 보간이 필요하면 정확한 시작·목표 정수를 보관하고 제한된 0~1 진행률로 차이만 계산하며 종료 시 목표 정수를 직접 대입한다. 출시 전 `long.MaxValue` 근처와 표시 단위 전환도 검수한다. 이번 연출에서 K/M 축약 규칙을 새로 도입하지는 않는다.

## 실제 획득량과 화면 표시량

실제 보상은 기존 전투 규칙이 정하는 시점에 기록한다. 젬의 비행 성공 여부나 DOTween 완료 콜백이 영구 지갑을 수정해서는 안 된다. 영구 지급은 기존 `RunResult → App → Progression`의 정산 정책을 유지한다.

종류별로 다음 값을 따로 관리한다.

| 값 | 의미 |
|---|---|
| 실제 획득량 A | Combat이 이미 확정한 이번 전투 보상 |
| 도착 누적량 C | 비행이 도착해 표시 처리가 확정된 금액. 종료·화면 교체 동기화는 별도 경로 |
| 화면 표시량 D | 현재 Text (TMP)에 표시하는 보간 중 정수 |
| 미도착량 | 아직 비행 중이거나 표시 대기인 금액 A−C |

항상 `0 ≤ D ≤ C ≤ A`를 유지한다. 모든 연출이 끝나면 `D = C = A`다. 예를 들어 실제 가넷이 100에서 143으로 늘어도 도착 전 HUD는 100을 유지한다. 대형 4개·소형 3개가 순서대로 도착하면 목표는 110 → 120 → 130 → 140 → 141 → 142 → 143이 된다.

현재 `CombatGemstoneList.ShowRunning`의 직접 숫자 덮어쓰기는 제거하고, 행의 표시 여부만 현재 전투 데이터와 맞춘다. 수량은 표시 전담 컨트롤러가 유일하게 쓴다. UI가 새로 만들어지거나 효과 기능이 꺼진 경우에는 실제 누적량과 즉시 동기화하는 명시적 경로를 둔다.

## 보상 사건과 중복 방지

`CombatRewardResolved`는 최종 기록된 보상을 전달하는 값 타입이다. 한 처치에서 최종 확정된 보상들을 묶어서 알린다.

- `RunId`, 런 내 증가하는 보상 사건 번호, 재화별 최종 증가량, 적용 전 캡처한 출발 월드 위치를 포함한다.
- 출발점은 사망 연출이 몬스터를 비활성화하기 전에 얻은 몸 중심이다. 현재 `DamageTextPosition`은 체력바/머리 위 위치이므로 그대로 재사용하지 않는다.
- 중복 처치 차단과 확률·유물·소수 이월·오버플로 검사를 거쳐 실제 장부에 기록한 증가량만 전달한다. 같은 ID가 기본/추가 보상으로 겹치면 정규화한다.
- 보상 계산·검증과 기록의 경계를 정리해 숫자 오버플로 실패 후 일부 보상만 표시되는 경우를 막는다. 드롭 확률과 실제 지급 정책은 바꾸지 않는다.
- `(RunId, 사건 번호)`로 중복 소비를 막는다. 풀 오브젝트는 별도의 재사용 세대 번호를 검사해 이전 비행의 콜백이 새 비행을 완료시키지 못하게 한다.
- 사건이 없거나 금액이 0인 사망에는 획득 젬을 만들지 않는다. 부활·반복 타격·대상 파괴가 추가 획득의 근거가 될 수 없다.

전투 난수와 표시 난수는 분리한다. 소비자는 몬스터 GameObject의 생존에 의존하지 않고 사건에 복사된 값만 사용한다.

## TargetPoint 연결과 화면 좌표

사용자가 지칭한 `PlayerProgressionPresentation(Clone)`가 실제 런타임 HUD 루트라면 생성 직후 그 인스턴스의 재화 ID별 바인딩을 등록한다. 현재 체크아웃의 Main에는 `GemStoneLists`와 6개 행이 있으므로 이 구성을 우선 연결 대상으로 삼는다. 두 경우 모두 `gem.garnet` 같은 고정 ID로 TargetPoint·텍스트·아이콘을 연결한다.

최종 목적지는 **각 재화의 획득 수량 텍스트**다. TargetPoint를 그 텍스트의 고정 표시 영역 중심과 일치시키고, 아이콘은 종류를 식별하는 시각 참조로만 사용한다. Inspector의 착점 오프셋은 텍스트 중심을 기준으로 적용하며 기본값은 0이다. 한 종류의 젬은 다른 종류의 수량이나 전체 합계 텍스트로 가지 않는다.

`GameObject.Find("PlayerProgressionPresentation(Clone)")`나 반복적인 이름 검색은 사용하지 않는다. 직렬화 참조 또는 HUD 생성자가 넘긴 참조를 사용하며, 해당 HUD를 해제할 때 등록도 함께 해제한다.

월드 카메라의 처치 위치를 화면에 투영하고 효과 Canvas의 로컬 좌표로 변환한다. Overlay Canvas는 UI 카메라가 없다는 현재 구성을 반영한다. 비행은 전용 효과 Canvas 안에서 수행하고 매 프레임 몬스터를 따라다니지 않는다.

화면 비율·해상도·UI 배율이 바뀌거나 행이 활성화되면 레이아웃 확정 후 여섯 착점만 다시 계산한다. 비행 중 목표 위치는 최신 착점으로 부드럽게 이어간다. 창 크기 변경 때문에 원래 목적지에 도착한 뒤 순간 이동하는 현상을 허용하지 않는다.

비행 계층은 게임 필드와 HUD 행 배경 위, HUD 숫자 아래에 둔다. 필요하면 고정 배경·비행 효과·숫자 전경의 Canvas 정렬을 분리해 숫자 중심까지 젬이 보이도록 한다. 효과 계층에는 GraphicRaycaster와 Raycast Target을 사용하지 않는다. 빈 HUD 영역 전체를 덮는 투명 패널로 전투 입력을 막지 않는다.

## DOTween과 풀의 소유권

젬마다 풀에서 재사용하는 진행률 Tweener 하나로 등장·분출·가속·축소를 평가한다. 숫자 행에는 각각 최대 하나의 스케일 Tweener와 수량 Tweener를 둔다. 매 처치마다 여러 Sequence와 캡처 람다를 만드는 방식은 기본 구현에서 제외한다.

Tweener는 초기화 때 만들고 재사용한다. 고정된 풀 슬롯이 보유하는 트윈은 `SetAutoKill(false)`로 유지하고 명시적으로 정지·되감기·해제한다. 풀 반환 시 위치·스케일·알파·색·표시 금액·사건 번호를 모두 초기화한다. DOTween 용량은 프로젝트의 다른 사용자까지 고려해 미리 설정한다. 재사용·수명주기 API는 [DOTween 공식 문서](https://dotween.demigiant.com/documentation.php)를 따른다.

일시정지는 이 연출 소유자의 시계로 제어한다. 현재 전투 일시정지가 항상 `Time.timeScale = 0`을 뜻하지 않으므로, 전역 시간 배율만 믿지 않는다. 전용 Tweener를 Manual 업데이트하거나 소유 그룹만 명시적으로 Pause/Play한다. 전체 게임의 `DOTween.KillAll`·`Clear`를 호출하지 않는다.

`SetLink`를 보조적으로 쓰더라도 풀 반환·씬 해제·구독 해제는 직접 처리한다. Sequence 내부의 자식 Tweener에 건 `SetLink`만으로 수명주기를 보장하지 않는다. [DOTween 공식 수명주기 설명](https://dotween.demigiant.com/documentation.php)

현재 설치에서는 코어 DLL에 있는 `Transform.DOScale`과 `DOTween.To`만으로 필요한 기능을 구성한다. TMP는 `TMP_Text` 값을 표시하는 대상이며 `DOTweenModuleTMP`나 Pro 전용 TMP 애니메이터는 필요하지 않다. DLL 접근과 `CursorHunter.App` 컴파일은 구현 단계에서 확인하고, 모듈 확장이 실제로 필요할 때만 공식 Setup의 asmdef 생성을 사용한다. 설치 파일 확인을 컴파일 성공으로 표현하지 않는다.

## Main 씬 컨트롤러와 Inspector

Main의 전투 프레젠테이션 관리 계층에 **`GemstoneCollectionController` 한 개를 씬에 미리 배치**한다. 전투 중 임의로 컨트롤러를 생성하거나 사용자가 프리팹 내부를 찾아다녀야 하는 구조로 만들지 않는다. 컨트롤러가 설정값·6종 바인딩·효과 풀·트윈·오디오·런별 표시 장부를 소유한다.

설정의 기준은 이 Main 컴포넌트의 직렬화 필드다. 관련 값은 한국어 설명, 단위, 허용 범위를 가진 접이식 그룹으로 묶는다. 별도 설정 에셋을 수정해야만 반영되는 이중 원본은 만들지 않는다. 필요하면 Unity Preset으로 컨트롤러 설정을 저장·적용한다.

| Inspector 그룹 | 조정 항목 | 초기값·동작 |
|---|---|---|
| 연결 | Combat 참조, 월드 카메라, 효과 Canvas, 풀 부모, 젬 뷰 프리팹, 아이콘 카탈로그 | 명시적 씬 참조. `Find`를 매 프레임 호출하지 않음 |

| 흡수 비행 | 전환 대기, 비행 시간 범위, 거리별 시간 보정, 발사 간격, 곡률 범위, 가속 곡선 | 0.03~0.07초, 0.28~0.52초, 0.012~0.028초 간격, 곡률 24~80px |
| 도착 효과 | 마지막 축소 시간, 텍스트 뒤 흡수광 크기·알파·시간, 잔상 사용/개수/간격 | 축소 0.05~0.08초, 잔상 최대 2개, 광도 제한 |
| 숫자 | 상단/하단 팝업 배율, 확대·복귀 시간, Ease, 최소 반응 간격, 숫자 보간 시간 | 1.12/1.16배, 0.055/0.15초, 0.15초 간격, 숫자 0.08~0.16초 |
| 색·가독성 | 종류별 숫자색, 최대 팝업 배율, 기존 외곽선·그림자 유지 | 현재 6종 밝은 색 유지. TMP 공유 재질을 실행 중 직접 수정하지 않음 |
| 사운드 | 기본/추가 젬 Clip, MixerGroup, 음량, 피치 범위, 발음 간격, 동시 음성 상한 | 피치 0.96~1.12, 최대 약 10회/초·8음성 |
| 성능 | 사전 풀 크기, 최대 활성, 추가 젬 예약, 프레임당 발사, 대기 항목 용량, 압력 시 최소 시간 | 256/256/64/24/1,024, 비행 최소 0.18초부터 조정 |
| 종료·효과 감소 | 종료 흡수 상한, 효과 감소 사용, 최소 동작·최대 팝업 | 종료 0.30초, 감소 모드 팝업 1.05배 |
| 검수 | 테스트 재화·수량·출발 Transform·반복 수, 미리보기 버튼, 활성/대기/미도착량 읽기 전용 | 43개·48개·80마리 테스트와 비우기. 실제 전투·지갑에 보상하지 않음 |

크기·시간·곡선·색·팝업·음량 변경은 Play Mode에서 **새로 시작하는 연출부터** 반영한다. 이미 비행 중인 젬은 시작할 때 캡처한 설정으로 마쳐 점프하지 않는다. 풀 크기·바인딩·프리팹 변경은 비활성 상태 또는 다음 런부터 적용한다. Inspector에 이 차이를 표시한다.

Play Mode의 임시 변경은 종료 시 사라지는 Unity 기본 동작을 명시한다. 조정 편의를 위해 `현재 조정값 복사`와 Edit Mode의 `조정값 붙여넣기`를 제공한다. 붙여넣기는 Undo와 씬 dirty 처리를 지원하며 연결 참조·런 상태·실제 획득량을 복사하지 않는다. 이렇게 저장한 값은 Main 씬에 남는다.

테스트 버튼은 실제 런이 진행되지 않는 Play Mode에서만 활성화한다. 테스트 전 표시값을 보관했다가 완료·비우기·화면 이탈 시 복원하고, 전투 시작 시 자동 종료한다. 이벤트 생산자·지갑·PlayerPrefs를 호출하지 않는 표시 전용 경로로 실행한다. 43개 테스트는 대형 4·소형 3을, 48개 테스트는 중형까지 눈으로 확인하는 기준이다.

`OnValidate`는 음수 시간·반경, 역전된 최소/최대, 소≥중 또는 중≥대 크기, 사전 풀/활성 상한 불일치, 잘못된 ID·중복 바인딩·누락 참조를 Inspector에 표시한다. 액면가와 보상량을 자동 수정하지 않는다. 런타임에는 시작 전에 잘못된 설정을 검증하고 연출이 실패해도 실제 보상 정산은 유지한다.

## 종료와 예외 상황

| 상황 | 사용자에게 보이는 동작과 정확성 |
|---|---|
| 시간 만료·정상 완료 | 전투와 정산은 먼저 확정. 이미 비행 중인 젬을 최대 0.30초 동안 빠르게 흡수. 남은 미발사량은 종료 시 최종값으로 동기화하고 결과 화면 표시 |
| 마지막 순간의 추가 드롭 | RunResult와 표시 장부를 대조해 누락분까지 마지막 수집에 포함 |
| 사용자가 즉시 결과/다음 화면으로 이동 | 기다리게 하지 않고 최종 표시량을 확정한 뒤 잔여 연출 회수 |
| 메인 메뉴 복귀·Reset | 비행·팝업·대기량을 즉시 정리하고 0으로 초기화. 실제 지급은 기존 SettlementPolicy 유지 |
| 새 전투 시작 | 새 RunId와 표시 세대로 시작. 이전 완료 콜백은 무시 |
| 검사창·수동 일시정지·포커스 상실 | 비행·숫자·소리를 함께 정지. 복귀 시 남은 시간부터 재개 |
| HUD 비활성화·교체 | 예전 바인딩 해제. 같은 런의 새 HUD에는 누적 사실을 재동기화 |
| 착점·아이콘·폰트 누락 | 실제 금액은 보존하고 해당 행에 즉시 동기화. 반복 로그를 제한하고 개발 빌드 진단에 표시 |
| 숫자 오버플로·시작 실패 | 기존 실패 정책을 우선하며 성공하지 않은 지급을 흡수 연출로 보여주지 않음 |

현재 `PresentationReset`을 젬의 즉시 회수 신호로 사용하면 정상 종료의 마지막 흡수도 사라진다. 데미지 숫자의 기존 초기화는 유지하고, 젬은 App에서 별도의 `FinishPresentation(result)`와 `CancelPresentation()` 경로로 관리한다. 실제 API는 `CompleteRun(result)`와 `CancelPresentation()`이다.

종료의 0.30초는 시각적 마무리 상한이다. 저장·지급 성공 여부를 애니메이션 완료에 매달거나 화면 이동을 막는 대기열로 만들지 않는다.

## 소리와 접근성

도착 순간의 짧고 둥근 수집음을 중심으로 한다. 모든 젬에 소리를 하나씩 재생하지 않고 50~80ms 이내의 도착을 묶는다. 전체 발음은 초당 약 10회, 동시 음성은 최대 8개에서 시작해 조정한다. 연속 흡수의 피치는 약 0.96~1.12 범위에서 완만하게 변하고 0.35초 이상 끊기면 돌아온다. 계속 높은 음으로 치솟는 연출은 넣지 않는다.

추가 젬 소리가 가넷에 묻히지 않도록 우선순위를 주고, 전투의 경고음을 가리지 않도록 믹서에서 상대 음량을 조정한다. 숫자 상승은 소리 없이도 이해할 수 있어야 한다.

효과 감소 설정에서도 소·중·대의 개수와 액면가는 유지한다. 분출·회전·잔상·흡수광을 생략하고 약 0.18~0.25초의 짧은 비행과 최대 1.05배 팝업을 사용한다. 이 설정에서 보상량·드롭 확률은 변하지 않는다.

## 구현 책임과 순서

| 순서 | 작업 | 확인하고 넘어갈 조건 |
|---|---|---|
| 1 | 설치된 DOTween 코어 참조, 실제 HUD 생성 위치, Main 컨트롤러와 Inspector, 6종 ID 바인딩 | App 컴파일 성공, 씬에서 설정 조정 및 6개 TargetPoint/TMP 연결 가능 |
| 2 | Combat의 최종 보상 사건과 App의 표시 장부 | 확률·유물·부활·중복·오버플로에서 금액이 정확함 |
| 3 | 고정 스냅샷 Sandbox에서 1·5·10 분해와 젬 1종의 풀·비행·도착·팝업 | 43개 = 대4·소3, 48개 = 대4·중1·소3, 도착 프레임과 실제 합계 일치 |
| 4 | Main 6종, 2열 HUD, 카메라/Canvas 변환과 종료 처리 | 실제 전투 시작·진행·정산·메뉴 복귀 연결 통과 |
| 5 | 개수를 보존하는 대기·분할 발사, 잔상, 오디오, 효과 감소, 성능 조정 | 목표 기기의 스트레스 테스트와 아트 검수 통과 |

Combat은 보상 사실을 만들고 App의 표시 계층이 HUD·풀·DOTween을 소유한다. Combat이 Progression의 지갑이나 Data의 아이콘 카탈로그를 직접 읽지 않는다. App은 기존 `GemstoneIconCatalog`를 사용한다. 공급사 원본은 수정하지 않고 게임 소유의 효과 프리팹과 조정 에셋을 둔다.

구현 구성은 `CombatRewardResolved` 사건, Main의 `GemstoneCollectionController` 총괄, `GemstoneFlyView` 풀 항목, `GemstoneCounterPresenter` 행별 표시다. 설정 구조체는 컨트롤러에 직렬화하며 별도 필수 설정 에셋은 두지 않는다. 공용 전역 이벤트 버스는 추가하지 않는다.

플랫폼과 최소 사양이 확정되지 않았으므로 성능 합격 수치는 해당 기기에서 최종 조정한다. 에디터 평균 FPS나 브라우저 미리보기로 출시 성능을 주장하지 않는다. Frame Debugger·Profiler로 Canvas 재빌드, 배치, 오버드로, 스파이크, 활성 트윈 수를 함께 확인한다. 동적인 UI를 별도 Canvas로 분리하고 비상호작용 UI의 Raycast를 끄는 근거는 [Unity의 UI 최적화 지침](https://unity.com/how-to/unity-ui-optimization-tips)을 따른다.

기획 미리보기는 분출·흡수·도착·팝업의 리듬을 논의하기 위한 것이다. 대화용 시안과 실제 Unity 구현은 별개다. Unity 구현에는 DOTween과 수집음을 연결했으며, 출시 기기의 성능·오디오 믹싱은 실제 전투에서 최종 조정한다.
