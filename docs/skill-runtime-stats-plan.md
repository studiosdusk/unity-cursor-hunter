# 자동 스킬 4종 런타임 스탯 개편안

작성일: 2026-10-15 · 상태: 스탯 합성·런 스냅샷 구현 완료. 강화 항목·단계·비용과 전체 정보 화면 표시는 후속

## 1. 목표와 경계

토네이도(`skill.tornado`), 헤드샷(`skill.headshot`), 벼락(`skill.thunder`), 화염 배기(`skill.flame_exhaust`)의 전투 수치를 `BaseStat + UpgradeStat → RuntimeStat`으로 계산한다. 각 스킬 컨트롤러는 현재 런의 `RuntimeStat`만 읽는다. 구매·저장은 Progression, 기본 전투 수치와 실행은 Combat, 전달과 런 시작 조립은 App이 맡는다. 전투 중 구매나 Inspector 수정은 현재 런의 수치를 바꾸지 않고 다음 런부터 적용한다.

이 개편은 스탯 전달 구조를 먼저 완성하는 작업이다. 어떤 능력을 몇 단계 강화할지, 단계별 수치·비용·선행 조건은 나중에 따로 정한다. 강화가 0일 때는 **전투 진입 시점의 Main 씬 설정으로 시작하는 동작과 수치가 동일해야 한다.** 스킬별 타격 규칙과 VFX 판정은 변경하지 않는다. 전체 정보 화면의 최종 스킬 수치 표시는 이번 범위에 포함하지 않는다.

## 2. 개편 전 구현 확인

| 스킬 | 현재 기본 동작 | 프리팹 기본값 | Main 씬 override | 지금 수치를 읽는 방식 |
|---|---|---|---|---|
| 토네이도 | 적이 없어도 필드 무작위 위치에 생성. 개수만큼 각각 이동·반복 타격 | 개수 1, 수명 5초, 공격력 ×2, 쿨타임 8초, 첫 발동 1초, 타격 간격 0.5초, 이동 속도 1 | 이동 속도 **4** | 개수·수명·쿨타임·피해는 `ConfigureForRun` 때 복사. 방향 전환·정지·타격 간격은 발동 때 읽음. 이동 속도는 `TornadoObject.Tick`에서 컨트롤러를 매 프레임 읽음 |
| 헤드샷 | 적이 있으면 무작위 지목. 폭발 전 대상이 죽어도 마지막 위치에서 폭발. 주 대상과 주변 대상의 피해 규칙이 다름 | 쿨타임 5초, 첫 발동 1초, 폭발 지연 1.15초, 효과 2.5초, 주변 공격력 ×2, 보스 주 대상 공격력 ×10 | 없음 | 주변·보스 피해는 런 시작 때 계산. 쿨타임·폭발 지연·효과 길이는 발동 때 컨트롤러에서 읽음 |
| 벼락 | 적이 없으면 준비 상태 유지. 무작위 적 1명에게 지연 후 단일 타격. 대상이 먼저 죽으면 연출만 진행 | 쿨타임 2초, 첫 발동 0초, 타격 지연 0.1초, 효과 0.5초, 공격력 ×4 | 쿨타임 **3초** | 피해는 런 시작 때 계산. 쿨타임·타격 지연·효과 길이는 발동 때 읽음 |
| 화염 배기 | 적이 없어도 커서에서 한 발씩 발사. 관통하며 투사체별로 한 몬스터를 한 번 공격 | 쿨타임 2초, 첫 발동 0초, 수명 1초, 속도 8, 커서 시각 크기 0.45, 피격 반경 배율 1.2, 공격력 ×1.5 | 쿨타임 **3초**, 수명 **3초**, 커서 시각 크기 **0.6** | 쿨타임·피해는 런 시작 때 복사. 수명·속도·크기·반경은 발동 때 읽음 |

표에서 생략한 현재 프리팹 값은 토네이도 방향 변경 주기 3초, 정지 확률 0.25, 정지 시간 0.75초, 소멸 축소 1초, 필드 가장자리 여백 1.5 월드 단위다. 화염 배기의 피격 이펙트 지속시간은 0.8초다. 현재 풀 상한은 토네이도 16개, 헤드샷 16개, 벼락 8개, 화염 배기 투사체 8개·피격 효과 80개다. 풀 크기 조정은 이번 스탯 구조 개편의 선행 조건으로 두지 않는다.

공통 공격력은 런의 `CombatSnapshot.AttackPower`를 사용한다. 스킬은 원시 피해를 `TryApplySkillDamage`에 전달하며, 치명타·공통 보스 피해 배율·처치·보상은 기존 전투 경로가 처리한다. 따라서 스킬 배율에 공통 보스 배율을 미리 곱하지 않는다.

개편 전에는 `SkillCombatSnapshot`과 `GameInformation.skills`에 ID와 해금 여부만 있었고, 데이터 검증은 토네이도 한 종류만 허용했다. 개편 후 네 스킬 ID와 스킬별 UpgradeStat 전달·검증을 지원한다. 실제 성장 데이터의 해금 노드는 여전히 토네이도 하나이며, 나머지 세 스킬은 에디터의 `Skill Acquired` 토글로 시험한다.

## 3. 데이터 정의

| 이름 | 소유·형태 | 포함할 값 |
|---|---|---|
| `BaseStat` | Combat의 스킬 컨트롤러 프리팹에 직렬화. Main 인스턴스 override 허용 | 현재 스킬별 전투 기본값. 기존 Inspector 설정의 후계 |
| `UpgradeStat` | Progression의 구매 노드에서 합산하고 Contracts의 읽기 전용 스냅샷으로 전달 | 스킬 ID + **명시적 stat ID** + 연산 + 증가량. 미구매·미정의 항목은 0 |
| `RuntimeStat` | CombatManager가 전투 진입 시 받은 현재 상태 스냅샷과 컨트롤러 Base를 합성한 스킬별 값 타입 | 유효 범위로 정리한 최종 쿨타임·개수·수명·배율 등과, 런 공격력을 적용해 계산한 원시 피해 |

네 스킬이 같은 **합성 절차와 계약**을 쓰되, `TornadoRuntimeStat` 등 스킬별 타입을 둔다. 모든 스킬에 빈 필드가 많은 거대 공통 클래스는 만들지 않는다. ID 문자열을 매 프레임 조회하거나 리플렉션으로 필드를 찾아 적용하지 않는다. 강화 노드의 stat ID는 표시명이나 노드 ID 끝부분에서 추측하지 않고, 허용 목록으로 검증한다.

초기 연산은 `add` 하나로 제한한다. 예를 들어 `cooldownSeconds` 강화값 `-0.2`는 `max(0.1, BaseCooldownSeconds - 0.2)`가 된다. 피해 배율 강화값 `+0.5`는 `BaseDamageMultiplier + 0.5`다. 개수 증가를 정의할 때는 정수만 허용한다. 단위는 초·월드 단위·배율·개수로 고정하고 NaN/Infinity, 알 수 없는 스킬·스탯, 허용 범위 밖 값을 오류로 처리한다. 나중에 여러 구매 노드가 같은 stat ID를 강화하면 Progression이 노드 순서와 관계없이 합산하고, 전투에 전달하는 스냅샷에는 stat ID당 합계 하나만 둔다.

장면·프리팹 참조, 카메라 패딩, 생성 평면, 히트박스 컴포넌트, VFX 재생 설정, 풀 **상한**은 설정값으로 유지한다. 화염 배기 피격 이펙트의 몬스터 크기 비례 배율도 이펙트 프리팹 설정에 남긴다. 이 값들은 첫 단계의 구매 가능한 `UpgradeStat`이 아니다.

## 4. 스킬별 RuntimeStat

아래 `BaseStat`에는 현재 동작을 결정하는 값을 모두 옮긴다. 강화 항목과 단계는 확정하지 않는다. 항목별 UpgradeStat이 아직 없으면 0을 합산해 Base 값을 그대로 RuntimeStat에 복사한다. 기존에 정한 화염 배기의 강화 방향은 쿨타임 감소다.

| 스킬 | RuntimeStat에 담을 값 | 보존할 특수 규칙 |
|---|---|---|
| 토네이도 | 개수, 수명, 공격력 배율·원시 피해, 쿨타임, 첫 발동 지연, 타격 간격, 이동 속도, 방향 변경 주기, 정지 확률·시간, 소멸 축소 시간 | 한 번 발동에 `count`개 생성. 각 토네이도는 독립 타격 시계 사용. `TornadoObject`의 이동 속도 참조도 현재 런의 값으로 교체 |
| 헤드샷 | 쿨타임, 첫 발동 지연, 폭발 지연, 효과 길이, 주변 피해 배율·원시 피해, 보스 주 대상 피해 배율·원시 피해, 일반전 주 대상 피해 정책 | 일반전 주 대상은 **폭발 순간의 남은 체력**을 원시 피해로 전달한다. 고정 배율로 바꾸지 않는다. 주 대상은 주변 피해 중복 제외. 대상이 먼저 죽으면 재지목하지 않음 |
| 벼락 | 쿨타임, 첫 발동 지연, 타격 지연, 효과 길이, 단일 피해 배율·원시 피해 | 지정한 한 대상에게만 한 번 타격. 타격 전에 죽으면 피해 없이 연출 종료. 일반전·보스전의 스킬 배율은 동일 |
| 화염 배기 | 쿨타임, 첫 발동 지연, 투사체 수명·속도, 커서 시각 크기 비율, 피격 반경 배율, 피해 배율·원시 피해, 피격 이펙트 지속시간 | 발동마다 작은 커서 하나. 향후 강화 방향은 쿨타임 감소이며 개수 증가는 계획하지 않음. 이전 발사체와 중첩은 허용. 한 발사체가 같은 몬스터를 다시 때리지 않음 |

첫 발동 지연·타격/폭발 지연·VFX 길이·기하 값은 일단 Base에서 Runtime으로 복사한다. 구매 강화 여부와 무관하게 컨트롤러가 발동 중 Base를 다시 읽지 않도록 하기 위해서다. 헤드샷·벼락의 쿨타임은 실제 발동 성공 시 갱신하고, 적이 없을 때는 준비 상태를 유지한다. 토네이도와 화염 배기는 적이 없어도 쿨타임을 소비한다.

## 5. 런 시작 흐름과 수명

```text
progression-config.en.json의 구매 노드 + 저장된 구매 ID
  → Progression: 스킬별 UpgradeStat 합산·검증
  → GameInformation / ProgressionCombatSnapshot: 해금 + UpgradeStat 복사
  → App: 전투 진입 시 현재 상태 스냅샷을 CombatManager에 전달
  → CombatManager: 컨트롤러 BaseStat + 스냅샷의 UpgradeStat + 이번 런 공격력
  → 스킬별 RuntimeStat 생성·검증 → 기존 풀 준비 → 런 시작
  → 컨트롤러/투사체/효과는 현재 RunId의 RuntimeStat만 사용
```

`SkillCombatSnapshot`을 해금 여부와 UpgradeStat을 담는 불변 전달 계약으로 확장한다. 이전 `(skillId, unlocked)` 생성자는 업그레이드 0으로 동작하게 보존해 Sandbox와 기존 테스트를 순차 이전할 수 있게 한다. 복사 방어를 적용해 구매 상태가 변해도 활성 런 값은 바뀌지 않게 한다. Combat은 Progression 설정 파일, PlayerPrefs, UI를 직접 읽지 않는다.

`HuntManager`는 전투 진입 시점의 스킬 상태 스냅샷을 `RunCoordinator.Start`에 전달한다. `CombatRunController.PrepareRun` 뒤 스폰 준비·`CommitStart` 전에 `ConfigureSkills`가 BaseStat과 UpgradeStat을 한 번 합성·검증한다. 준비 실패 시 활성 효과를 풀에 반환하고 런 전체를 취소한다. `CommitStart` 뒤에는 고정된 RuntimeStat으로 발동 시계를 연다.

RuntimeStat은 `RunId`에 묶어 고정한다. 일시정지는 런 시계를 멈추므로 남은 쿨타임과 효과 타이밍이 유지된다. 런 종료·중단·재시작 때 활성 효과와 풀 객체의 이전 `RunId` 참조를 지운다. 피격·폭발 콜백은 기존 `IsCurrentRun` 검사에 더해 현재 RuntimeStat의 런에만 유효하다. 구매, Inspector 조정, 커서 기본 공격 수치 변경이 이미 시작한 런을 바꾸지 않는다. 토네이도 이동 속도도 전투 진입 때 캡처한 값만 사용한다. 플레이 중 Inspector 변경은 테스트 상황으로만 보고 다음 런에 반영한다.

피해 환산은 기본 공격력 × 최종 스킬 배율을 `double`로 계산하고, 기존 스킬의 반올림(`MidpointRounding.AwayFromZero`)과 `long.MaxValue` 포화를 유지한다. 헤드샷 일반전 주 대상처럼 타격 시점에 결정되는 값은 RuntimeStat의 정책을 읽고 그때 대상의 현재 체력을 사용한다. 타격마다 스탯을 재합성하지 않는다.

## 6. 데이터·계약 이전

1. `game-data.en.json`의 `skills`에 네 ID를 지원하고 기존 토네이도 ID와 구매 기록을 유지한다. 실제 해금 노드의 비용·배치 등은 해당 스킬의 성장 기획을 정할 때 확정한다. 그전에는 에디터 시험 토글을 저장 구매와 분리해 유지한다.
2. `SkillCombatSnapshot`에 UpgradeStat 전달 공간을 마련한다. 아직 정해지지 않은 강화 항목은 빈 값으로 전달하며 RuntimeStat은 BaseStat과 같아진다. 향후 강화 노드를 정하면 명시적 `statId`, `operation: add`, 단위가 분명한 `value`를 성장 설정에 추가한다. 저장에는 구매 노드 ID만 남기고 RuntimeStat이나 합계 수치를 저장하지 않는다.
3. `GameInformation.skills`, JSON 스키마·예제, `SkillCombatSnapshot`, 빌더의 ‘스킬 1개/토네이도만’ 가정을 함께 해제한다. 기존 데이터와 저장의 이전 정책을 정하고 필요하면 스키마 버전을 올린다. 원본 영어 JSON과 한국어 참고본, 데이터 검증 스크립트도 같은 시점에 갱신한다.
4. 기존 개별 직렬화 필드를 `BaseStat` 묶음으로 옮길 때 프리팹과 Main/Sandbox의 실제 serialized 값을 한 번에 이전한다. Unity가 필드 경로 변경을 자동으로 보존한다고 가정하지 않는다. 특히 Main의 토네이도 속도 4, 벼락 쿨타임 3초, 화염 배기 쿨타임·수명 3초와 크기 0.6을 검증한다.
5. 전체 정보 화면에 최종 RuntimeStat을 보여주는 작업은 후속으로 남긴다. 이번에는 전투 계산과 화면 표시를 연결하지 않는다.

## 7. 검증과 완료 조건

- 강화 0인 Main/Sandbox에서 네 스킬의 첫 발동, 간격, 피해, 대상 선택, 효과 수명, VFX 크기·위치가 현재와 같다. 프리팹 기본값과 Main override를 각각 비교한다.
- 강화 0의 전달과 계산, 잠긴 스킬의 비발동, 네 스킬 ID의 게임 정보 → App → Combat 전달을 확인한다. 실제 강화 노드가 정해진 뒤에는 구매 노드 하나·여러 개 합산, 미구매 노드 무시, 저장 재로드, 잘못된 stat ID·값 거부를 추가 검증한다.
- 같은 RunId에서 재현 가능한 발동 순서, 일시정지·재개, 대상 소멸, 시간 만료 경계, 재시작과 오래된 콜백 무효화를 확인한다. 구매/Inspector 수정은 다음 런에만 반영된다.
- 풀은 현재 방식을 유지한다. 풀 상한·확장 정책을 이번 개편의 완료 조건으로 삼지 않는다.
- `python3 tools/validate_collaboration.py`, 데이터 스키마·참고본 검증, Unity EditMode/PlayMode 및 Main 수동 플레이 결과를 별도로 기록한다. 전체 정보 화면 검증은 후속 작업으로 둔다.

## 8. 권장 작업 순서

1. 강화 0 스냅샷·합성 함수·스킬별 RuntimeStat을 먼저 만들고, 네 컨트롤러의 Base 직독을 없앤다. 프리팹/씬 값을 이전하고 Sandbox에서 기존 동작을 확인한다.
2. Contracts 전달 타입, GameInformation의 네 스킬 지원, App의 전투 진입 스냅샷 전달을 묶어서 구현한다. 전투 시작 전에 CombatManager가 현재 상태를 한 번 받아 RuntimeStat을 완성한다.
3. 나중에 사용자 지정 강화 항목·단계·수치가 확정되면 Progression의 stat ID 합산과 구매 노드를 추가하고, 실제 구매 → 새 런 → 일반전/보스전 적용을 검증한다.
4. 전체 정보 화면의 최종 스킬 수치 표시는 별도 작업으로 진행한다.
